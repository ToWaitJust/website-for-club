## 第一部分：开发原则

> 原则是"为什么这样做"——遇到拿不准的情况，回到原则判断，而不是翻代码抄。
> 原则之间会互相约束（如"复用优先"与"契约先行"冲突时，以契约为准），按场景权衡。

### 1.1 分层架构原则（后端）

**核心：每一层只做自己的事，边界不能破。**

| 层 | 职责 | 硬性约束 |
|---|---|---|
| **Controller** | 参数校验、RBAC 权限注解、VO→BO 转换 | 不调用 Service 以外的业务逻辑，不引入 DO |
| **Service** | 业务校验、事务、跨 Mapper 聚合 | **只认 BO**，不反向依赖任何一端的 VO（PC/App 的 VO 都不行） |
| **Mapper** | 单表 + 受控复杂 XML 查询 | 继承 `BaseMapperX`，简单查询用 `LambdaQueryWrapperX`；ORM/Lambda 优先，**禁止手写 XML 原生 SQL** |
| **Convert** | MapStruct 做 DO/BO/VO 转换 | `unmappedTargetPolicy = ERROR`，**不得手写字段复制** |
| **DO** | 继承 `BaseDO`，一一映射数据库表 | 不含 `tenant_id`，不聚合跨表字段 |

**判断口诀**：Controller 问"谁在调、参数对不对"；Service 问"业务规则是什么、要不要事务"；Mapper 只回答"怎么查"。

**原生 SQL 例外**：默认使用 MyBatis-Plus 的 `BaseMapper` / **Lambda 表达式**（`Wrappers.lambdaQuery()`），日常开发多用 **Java 8 Stream** 在内存做数据组装/过滤/转换，减少不必要的数据库交互。仅在以下特定场景允许手写 XML SQL：① 超复杂多表关联（三张表及以上）；② 困难复杂的业务 SQL（嵌套子查询、窗口函数等）；③ 极致性能优化（经压测证明 Lambda 有瓶颈）。

来源：`项目开发准则.md`、`VO与BO架构分析及Outbox改造方案.md`

### 1.2 BO / VO 分层原则

- **VO（View Object）**：Controller 层 HTTP 契约，随端演进；PC 与 App **各自独立**，互不引用。
- **BO（Business Object）**：Service 层业务契约，与端无关；**两端共享同一套**。
- **Convert 各自独立**：`NoticeXxxConvert`（PC）/ `NoticeAppXxxConvert`（App）互不依赖。
- **入参 BO 化**：Service 方法入参一律 BO（`XxxPageQueryBO` / `XxxCommandBO`）；**单用途操作用独立命令 BO**（如 `UpdateRecipientCommandBO`），避免复用全量编辑命令造成字段覆盖。
- 出参允许 VO（与前端契约绑定后强行 BO 化风险大），分页行可用 BO 作事实标准。

来源：`VO与BO架构分析及Outbox改造方案.md`

### 1.3 契约先行原则

- **先定接口契约，再写实现**：后端先产出 Controller 路由 + VO 字段，前端字段必须与后端 VO **完全一致**（时间统一毫秒时间戳 `number`）。
- **Boolean 语义必须确认**：如 `noticeStatus`：false=发布（可见）、true=回收（隐藏）；`replyDeleteEnabled`：0=允许删除、1=禁止删除。前后端渲染与校验必须同一语义。
- **前后端权限三处同源**：Controller `@PreAuthorize`、菜单 SQL 权限标识、前端 `v-hasPermi` 必须一致（格式 `notice:<模块>:<action>`）。
- **原型 ≠ 需求**：Vue2 原型仅作需求参照，**不可直接拷贝**；与需求文档冲突时以需求文档 + 已落地后端 VO 为准（如回复删除 `replyDeleteEnabled` 已落地）。
- **未确认的事项不猜着做**：字段缺失、语义歧义、缺接口，先列"待确认点"找甲方闭环（见 2.2），确认后才动手。

来源：`前端开发准则.md`、`uniapp开发与编译验证流程.md`、`day-one-发件箱开发.md`

### 1.4 复用优先原则

开发新功能前**先盘点可复用能力**，能复用就不新建：

- 后端：`NoticeCurrentUserResolver`（当前用户解析）、共享 Mapper（NoticeInfo/Recipient/TagRelation/Attachment/Reply）、共享常量与错误码段、`NoticeAttachmentService`（附件上传/验证/补偿）。
- PC 前端：收件箱/标签/分组是**模板来源**（`src/api/notice/*`、`src/views/student/notice/*`），新模块照此组织。
- App 前端：`../inbox/constants.js` 公共函数、`@/utils/noticeConstants.js` 全局常量直接复用。

**先确认"甲方 dev 已存在"的共享表/接口，不执行无关 DDL，不重复造轮子。**

来源：`项目开发准则.md`、`前端开发准则.md`、`uniapp开发与编译验证流程.md`

### 1.5 幂等与安全原则

- **菜单/种子 SQL 必须幂等**：`INSERT ... WHERE NOT EXISTS` + 组件地址去重，重复执行不产生脏数据。
- **附件对象级授权**：附件预览/下载按"对象归属"鉴权（发布者本人 或 拥有大厅查询权限），不能只按登录态放行。
- **越权隔离**：发件箱写操作 + 详情/回复/评分/附件下载均校验操作人归属（`teacherNo.equals(senderNo)`）；大厅是管理员全局视图（不校验归属），二者边界要清晰。
- **身份信息服务端解析**：发布人身份从当前登录用户解析（复用 `NoticeCurrentUserResolver`），**不可由客户端传入**。
- **SQL 注入**：动态 SQL（MyBatis XML）用安全写法（`#{}` 参数绑定），禁止字符串拼接。
- **前端错误提示不暴露敏感信息**：页面 catch 只清数据，错误提示交给请求层统一处理。

来源：`项目开发准则.md`、`审查清单-发件箱与通知大厅.md`、`前端开发准则.md`

### 1.6 增量与最小改动原则

- **不破坏已交付功能**：新阶段只做增量（Day2 不修改 Day1 已交付的接口和数据模型）。
- **最小改动面**：改一个功能，只动相关文件；跨模块支撑改动（infra/system）要评估耦合度并单独审查。
- **失败可回滚**：界面开关类操作失败要恢复原值；上传失败要补偿删除；编辑失败不影响原数据。
- **向后兼容**：wire 契约（接口路径与字段）已绑定前端后，改造内部实现（如 VO→BO）保持前端无感。
- **跨模块交互**：严禁跨模块直接调用/强依赖，不同业务模块之间通过对外暴露的 Service API / Feign / RPC 接口调用，不引入其他模块内部实现类。
- **前端响应统一包装**：Controller 统一返回标准包装对象（如 `CommonResult<T>`），明确状态码、错误提示与数据结构。
- **枚举字段映射**：枚举类包含 `code`（值）和 `desc`（描述），并提供 `byCode(code)` 方法，配合管理端字典管理使用。
- **错误码集中管理**：业务异常的错误码与提示统一在 `ErrorCodeConstants` 中按模块划分区间维护，**禁止直接抛硬编码字符串**。
- **日志规范**：用 `@Slf4j` 记录日志；关键业务节点（创建/状态变更/第三方调用）记录关键入参和返回结果；**禁止 `System.out.println` / `e.printStackTrace()`**。

来源：`day-two-发件箱开发.md`、`VO与BO架构分析及Outbox改造方案.md`、`审查清单-发件箱与通知大厅.md`

### 1.7 前端规范原则（PC 管理端）

- `<script setup lang="ts">`，禁止 Vue2 Options API / Vuex / uni-app 标签。
- HTTP 一律用 `import request from '@/config/axios'`；接口封装放 `src/api/<域>/index.ts`，类型与后端 VO 一一对应。
- 页面放 `src/views/student/<域>/`，camelCase 子目录；`defineOptions({ name: 'Xxx' })` 必须与后端菜单"组件名"一致（否则 keep-alive 失效）。
- 业务常量集中到模块 `constants.ts`，**禁止魔法数字**；状态值用统一工具渲染（如 `getTagStyle`），不写死颜色。
- 提交前必跑 `npm run lint:eslint` + `npm run ts:check`（开发期用 `ts:check:notice` 约 30 秒）。
- 快速筛选/翻页用递增序号（`requestSerial`）丢弃过期响应，防串数据。
- 复杂交互拆独立子组件（Dialog/Drawer），`ref` + `open(id)` 暴露给列表页；`index.vue` 只负责列表。
- **PC 样式原则**：本项目**无独立 UI 设计稿**，以现有需求及已确认页面效果为最终样式标准。**不得擅自调整**页面整体布局/模块位置/交互结构/主要样式；发现布局不合理或确有调整必要时，**提前向项目负责人说明原因与方案，确认后再改**；小范围优化（间距/对齐/文字溢出/尺寸适配）不影响整体结构的可自行处理。

来源：`前端开发准则.md`、`day-one-发件箱开发.md`

### 1.8 App 规范原则（uni-app / Vue2）

- `npm install --legacy-peer-deps`；用 npm 不用 pnpm。
- 新页面必须在 `pages.json` 注册；图片放 `static/images/<模块>/`，代码中**绝对路径**引用（`/static/...`）。
- Vue2 模板**禁用可选链 `?.`**，改 `(a && a.b) || ''`；复杂弹窗用视图切换代替嵌套 popup。
- 附件不能直接用对象路径，必须走后端鉴权端点（`/app/notice/xxx/attachment/preview|download?id=`）并携带鉴权头。
- 列表页生命周期分页模式：`onLoad` 首载 → `onPullDownRefresh` 重置 → `onReachBottom` 追加 → `onUnload` 使在途响应失效（revision 令牌防串）。
- rpx 按 375 基准设计（`1rpx = 0.5px`，设计稿 px × 2 = rpx）；webview 嵌入页禁止自带顶部导航栏、禁用 vw/vh。

来源：`uniapp开发与编译验证流程.md`、`uniapp-ui调整指南.md`

### 1.9 Git 协作原则

- **main/master = 正式发布版，不直接开发**；协作统一在 `feature/notice` 分支。
- **推送前必拉取**：`commit → pull --rebase → push` 三步不能跳；用 `--rebase` 保持历史干净。
- **永远不要 `git push -f`**（会覆盖合作者代码）。
- 提交信息规范：`模块名：具体改动`，写完一个功能点就 commit，不攒大提交。
- **本地配置文件不推送**：`application-local.yaml`、`.env.local` 等用 `git update-index --skip-worktree <文件>` 标记不跟踪（新克隆仓库需各自执行一次）。
- 本地构建环境修复（postcss.config.js、postcss 版本等）属于本机配置，**不强行提交覆盖团队约定**；跟踪文件的代码修复正常走 git。
- 大改动前先与合作者沟通，避免撞车。
- **GitFlow 工作流**：代码仓库 `http://internal.fzjszn.cn:3000/`。功能开发基于 `feature/*` 分支（如 `feature/notice`），从最新主干创建；分支命名 `feature/功能简要描述`（如 `feature/user-login-optimize`）。
- **合并流程（重要）**：本地 feature 分支开发并提交（`commit` 信息清晰）→ 推送远程（`push`）→ **在 Git 仓库「合并请求」界面发起 MR**（向主干发起）→ 通知项目负责人/审查员审核 → **等待负责人审核后合并**。**切勿自行合并**，合并由项目负责人或指定审查员完成。

来源：`Git协作开发操作指南.md`、`APP端H5渲染异常排查与修复.md`

### 1.10 测试伴随原则

- **代码与测试同步写**：核心 BO/Service 写完即配单元测试，不攒到最后。
- 服务集成测试：继承 `BaseDbUnitTest`（H2 内存库 + 真实 Mapper），Proxy 打桩外部 API，`SecurityContextHolder` 模拟登录，`AssertUtils.assertServiceException` 断言错误码与消息。
- 自测顺序遵循"链路"而非"页面"：列表 → 筛选 → 详情 → 操作 → 删除，覆盖正常 + 越权 + 边界 + 事务回滚。
- 提交前按 `审查清单` 自查（接口契约一致性、权限、附件安全、N+1、事务、SQL 注入、菜单 seed 幂等、前端状态同步、移动端适配、异步任务冲突、测试覆盖）。

来源：`项目开发准则.md`、`发件箱与通知大厅测试地图.md`、`审查清单-发件箱与通知大厅.md`

### 1.12 平台化统一管理原则

**核心：能用管理端/SQL 注册的配置，一律不在代码里硬编码；操作留痕、全局变更必同步。**

- **字典管理**：所有"可被配置、可能被修改的枚举/状态值"必须通过管理端注册字典（系统工具 → 数据字典），做到好维护、统一管理。适用场景：通知状态（发布/回收）、回复类型（禁止/单次/自由）、评分语义、菜单类型、任务状态等。禁止在代码里散落硬编码枚举值。
  - 操作路径：管理端 → 系统工具 → 字典管理 → 新增字典类型（dictType 全局唯一、小写下划线，如 `notice_reply_type`）→ 新增字典数据（label 中文、value 数字、排序控制展示顺序）。
  - 后端消费：通过 `IDictFrameworkService` / `getDictList(dictType)` 接口读取，或前端调 `/admin-api/system/dict-data/simple-list` 取选项；**禁止在代码里散落硬编码枚举值**。
  - 注意：字典 value 与后端 VO/枚举必须一一对应；新增字典后若影响前端下拉/状态展示，需同步告知前端。
- **菜单管理**：PC 端与 App 端的菜单**必须通过管理端注册**（系统工具 → 菜单管理），不直接写 SQL 插入菜单表。
  - 权限标识：yudao 规范 `notice:<模块>:<action>`（如 `notice:outbox:query`），与 Controller `@PreAuthorize`、前端 `v-hasPermi` **三处同源**。
  - 图标：**统一使用 MinIO 对象存储 URL**（先上传图片到 MinIO → 菜单图标字段填 MinIO URL），好处：可随时替换图标而不重新部署。
  - 菜单类型：目录 / 菜单 / 按钮；按钮级权限用于细粒度操作控制。
  - seed SQL：新模块首次上线同步产出幂等 seed SQL（`ssa_notice_*_menu_seed.sql`），`INSERT ... WHERE NOT EXISTS` + 组件地址去重。
  - PC 组件地址为 `student/notice/outbox/index`（views 下相对路径）；App 菜单无组件地址，配 portal 与路由。
- **定时任务注册**：所有定时任务**必须通过管理端注册**（基础设施 → 定时任务）或 seed SQL，不直接改代码里的启动开关。
  - 字段：任务名称（可读）、Handler 名称（`@Job` 注解名，如 `noticeTopExpireJob`）、Cron 表达式（如 `0 */5 * * * ?`）、状态（开启/暂停）。
  - **关键提醒**：写了 Job 类 ≠ 任务会跑——必须在管理端注册（或 seed SQL）才生效；Handler 名称写错则任务报错但不执行。
  - 启停直接管理端操作，不需改代码或重启。
- **角色/用户创建**：新手开发者**不要自己去创建**；创建角色/用户**必须通过管理端**（系统设置 → 用户与角色 / 角色管理），**禁止直接 SQL 插入**（安全审计、权限关联会断裂）。
  - 创建后务必分配菜单权限 + 角色权限，确认用户可登录、菜单可见、按钮权限生效。
  - 密码重置、角色调整属敏感操作，操作人确认权限后执行。
- **信息同步（全局规则）**：以上四类配置（字典、菜单、定时任务、角色/用户）有任何更新，**必须在群聊中告知**，包含：操作内容、影响范围、是否需前端配合。尤其是**全局性、可复用的操作**（如新增跨模块共享字典、注册被多模块复用的定时任务），**必须主动同步**，避免覆盖他人配置或造成联调信息差。

### 1.13 前端体验与性能原则

**核心：性能上"少请求、批量取、不 N+1"；体验上"有反馈、不闪退、加载保样式、体感丝滑"。**

**A. 效率与性能**

- **禁止 N+1 循环慢查询**：列表/详情数据必须在服务端按分页查询 + 批量组装返回，**绝不允许在前端循环里逐条发请求**。
- **多用分页查询**：触达列表、回复列表、评分列表、附件列表等大数据场景一律分页加载（App 下拉刷新 + 触底加载），禁止一次性拉全量。
- **复用已有数据**：详情页已在列表/上级拿到的数据不重复请求；跨组件共享通过 props/状态传递，不重复调接口。
- **大字段按需取**：列表不查正文等大字段，详情单独取。

**B. 用户体验（反馈 / 不闪退 / 丝滑）**

- **操作必须有反馈**：关键操作给成功/失败提示；耗时操作给 loading 或骨架屏。
- **不要闪退、不要大幅回收**：加载时**保持原有样式结构**（用骨架屏/占位块），避免整块消失又出现导致页面抖动；优先局部更新，**不要整表/整页重渲**。
- **区分实时查询与单次查询**：
  - **实时查询**（标题搜索、关键字筛选、状态切换、日期变化）→ 加**防抖**（如 300ms）+ 递增**请求序号**丢弃过期响应（`requestSerial`），避免连续触发导致串数据或白屏。
  - **单次查询**（打开详情、新建/编辑提交、置顶/状态开关）→ 单次请求 + loading 遮罩/按钮锁定，成功后刷新局部数据。
- **保留上下文**：翻页/切换时记住滚动位置、已选状态、筛选项，不丢失用户已操作内容。

**C. 校验与错误提示**

- **该给的提示都要给**：必填缺失、格式错误、长度超限、业务规则违反（如"至少选择一名收件人"）都要有提示。
- **错误提示按需求与业务场景定优先级**：关键业务错误（越权、重复提交、数据冲突）用醒目提示（错误弹窗/红色）；普通格式错误用表单内联提示（轻量）。**提示文案贴近业务、不暴露技术细节**。
- **前后端双重校验**：前端提交前预校验（体验优先），后端做兜底校验（安全兜底）。

**D. App rpx 自动适配**

- App 端布局**一律用 rpx 自动适配所有设备**，禁止用 px 写布局尺寸；按 375 基准（`1rpx = 0.5px`，设计稿 px × 2 = rpx）。
- H5 桌面预览统一按 375 基准，不随窗口宽度放大（`main.js` 设 `rpxCalcMaxDeviceWidth = 0`）。
- 图片、弹窗高度、按钮尺寸全部用 rpx；弹窗/长列表用 `flex` + `max-height`，禁 vw/vh，避免不同机型溢出或撑破。
- **开发调试**：浏览器"开发者模式"（F12）设备仿真设 **875×812**（iPhone 尺寸），此尺寸下 rpx 是 px 的两倍；蓝湖切图可切换 rpx 直接取尺寸。

来源：`前端开发准则.md`、`uniapp-ui调整指南.md`、★经验

### 1.14 代码规范与注释原则

**A. 命名规范**

- **驼峰命名法**：类名大驼峰（PascalCase，如 `StudentController`）；方法名、变量名、参数名小驼峰（camelCase，如 `studentId`、`getStudentInfo`）。
- **常量与枚举**：全大写，单词间用下划线（如 `MAX_RETRY_COUNT`）。
- **实体职责严格划分**，禁止混用：

| 对象 | 全称 | 核心职责 | 对应关系 |
|---|---|---|---|
| **DO** | Data Object | 数据库实体对象 | **严格对应数据库表**，一属性一字段，用于 Dao/Mapper 层持久化 |
| **DTO** | Data Transfer Object | 数据传输对象 | 服务层之间/远程调用（RPC）传递复合数据，多用于模块间调用 |
| **VO** | View Object | 视图展示对象 | 后端向前端响应数据，只含展示字段，起数据裁剪与安全过滤 |
| **BO** | Business Object | 业务对象 | 复杂业务逻辑处理，由 Service 层构建，聚合多 DO/DTO 做校验与计算 |

- **见名知意**：严禁无意义单字母（循环变量 `i`/`j` 除外）或拼音缩写（如 `yhbh` 应写 `userCode`）。

**B. 注释规范**

- **类与接口**：每个类、接口必须编写类注释说明核心功能。
- **方法注释**：核心业务方法用 Javadoc（`/** ... */`），含功能简述、`@param`（参数及取值范围）、`@return`、`@throws`。
- **行内注释**：复杂业务逻辑/算法核心/关键判断必须添加行内注释，解释**"为什么这么做"（Why）**而非仅"做了什么"（What）。
- **禁止冗余注释**：如 `int a = 1; // 定义a等于1`。

来源：`项目前期开发指南.md`、★经验

### 阶段 2：方案设计与契约定义

1. **接口契约**：Controller 路由（`/notice/<模块>/<动作>`）+ 请求/响应 VO 字段 + 权限标识（`notice:<模块>:<action>`）+ 错误码（追加到 `ErrorCodeConstants.java`，用预留段如 `1-058-006-xxx`）。
2. **BO 设计**：入参全部 BO 化（`XxxPageQueryBO extends PageParam` / `XxxCommandBO`）；单用途操作独立命令 BO；两端 Convert 各自独立。
3. **数据库设计**（如涉及）：优先复用共享表；新表/新字段整理 DDL，**开发者直接在测试库执行**（无需交他人，减少工作量）。
4. **方案评审**：分层是否合规、复用是否到位、权限与越权边界、事务边界、性能（分页 N+1）、是否影响已交付功能。
5. 输出最终接口清单（参考 `notice-outbox-hall-home-api-snapshot.md` 的格式）。

### 阶段 3：数据库变更（如涉及）

1. **先读数据库设计文档**：数据库设计由项目经理统一产出《数据库设计文档》，开发者**只需从该文档了解表结构与字段语义**，无需自行重复设计；表/字段变更以该文档为准。
2. 复用已存在表（`notice_info`、`notice_recipient`、`notice_tag_relation`、`notice_reply`、`notice_attachment`、`notice_score`、`notice_pack_task` 等），不执行无关 DDL。
3. **DDL 谁用谁执行**：本项目数据库为**测试库**，**开发者可直接在测试库执行自己的 DDL 操作文件**，无需交他人，减少工作量。
4. **不要大批量把数据库操作文件堆给项目经理**：各模块开发者各自维护各自模块的 DDL 并自行在测试库执行，徒增项目经理工作量且拖慢节奏。
5. 新菜单/权限：写幂等 seed SQL（`ssa_notice_*_menu_seed.sql`），`INSERT ... WHERE NOT EXISTS` + 组件地址去重。

**3.5.1 字典管理**

**3.5.3 定时任务注册**

| 项 | 内容 |
|---|---|
| 操作路径 | 管理端 → 基础设施 → 定时任务 → 新增任务 |
| 字段 | 任务名称（可读）、Handler 名称（`@Job` 注解名，如 `noticeTopExpireJob`）、Cron 表达式（如 `0 */5 * * * ?`）、状态（开启/暂停） |

| 关键提醒 | **写了 Job 类 ≠ 任务会跑**：必须在管理端注册（或 seed SQL）才生效；Handler 名称写错则任务报错但不会执行 |

### 阶段 4：后端开发

按 **BO/VO 定义 → Mapper → Service → Controller → Convert → 错误码/常量 → 菜单 seed → 单元测试** 顺序：

1. **定义 BO/VO**：字段与数据库/前端契约对齐；时间类型确认（`LocalDateTime` ↔ 毫秒时间戳）。
2. **Mapper**：继承 `BaseMapperX`；复杂查询写 XML，**先分页 ID 再批量读详情，避免 N+1**；统计类查询注意口径。
3. **Service**：业务校验、事务（`@Transactional` 边界正确）、跨 Mapper 聚合；归属校验（例外：回显 `getNotice` 不校验、大厅全链路不校验）；逻辑删除走 `@TableLogic`。
4. **Controller**：参数校验（jakarta.validation）、`@PreAuthorize` 权限注解、Convert 桥接 BO。
5. **Convert**：MapStruct，`unmappedTargetPolicy = ERROR`，字段缺失编译期报错，不允许手写复制。
6. **错误码与常量**：业务状态用枚举/集中常量，**禁止魔法值**（参考收件箱既有常量类）。
7. **单元测试**：随代码同步写（见原则 1.10）。
8. 编译验证：`mvn -o compile -pl smart-student-affairs-notice -am -q` 通过。

### 阶段 5：前端开发（PC / App）

**PC 管理端**：

1. API 层：`src/api/<域>/index.ts`，`export type/interface` 声明模型（与后端 VO 一一对应，时间毫秒时间戳）+ `export const xxxApi` 封装（URL 与 Controller 完全对齐）+ JSDoc 说明业务语义。
2. 页面层：`src/views/student/<域>/`，`index.vue` 只负责列表（ContentWrap + el-form + el-table + Pagination）；复杂交互拆独立子组件（Dialog/Drawer），`ref` + `open(id)` 暴露。
3. 行内开关（置顶/状态）：调最小接口，**失败回滚原值**，成功刷新列表。
4. 表单提交前做类型互转（字符串枚举 ↔ 后端布尔/数字），参照需求文档与已落地 VO。
5. 检查：`npm run lint:eslint`、`npm run ts:check:notice`。

**教师 App**：

1. API 层：`api/notice.js` 追加方法（方法名=后端语义，分页参数 `pageNo/pageSize`）。
2. 页面层：`pages/teacher/notice/<域>/`，先注册 `pages.json`；复用 `constants.js` 公共函数。
3. 生命周期分页：`onLoad` 首载 → `onPullDownRefresh` 重置 → `onReachBottom` 追加 → `onUnload` 使在途响应失效；**revision 令牌防串**。
4. 弹窗组件：全局 `uni-popup` + `$refs.xxx.open()`；复杂弹窗用视图切换；Vue2 模板不用 `?.`。
5. 检查：编译日志过滤本模块 ERROR。

| 10 | webview 嵌入后 UI 层级混乱、双导航栏 | 页面自带顶部导航栏 + 宿主导航栏并存 | webview 页面**禁止顶部导航栏**，返回走 `postMessage`；布局用 rpx/%/flex，禁用 vw/vh | uniapp-ui指南 |
| 11 | 页面顶部内容被状态栏遮挡 ★ | 未预留状态栏高度（刘海屏/全面屏） | 用 `getStatusBarHeightPx()` 计算顶部 padding（webview 嵌入页除外——由宿主控制） | uniapp-ui指南 / ★经验 |
| 12 | token 过期后接口全 401，页面无感知 ★ | 未统一处理会话过期 | 请求层拦截 401 → 跳登录/刷新 token（`utils/session.js` 已有会话过期处理，复用） | uniapp流程 / ★经验 |
| 13 | 图片加载慢/大图卡顿 ★ | 原图过大 | 图片压缩/懒加载；列表用小图 | ★经验 |
| 14 | 不同机型样式大小不一致 | 布局用 px 写死 | 布局一律 rpx 自动适配所有设备（375 基准，px×2）；H5 桌面预览设 `rpxCalcMaxDeviceWidth = 0` | ★本补充 |
| 15 | 弹窗/长列表在长屏或小屏溢出、撑破 | 用 vw/vh 或固定高度 | 用 rpx + `flex` + `max-height`，禁 vw/vh；弹窗高度用 vh/rpx 并限 max | ★本补充 |
| 16 | 下拉刷新/触底加载连续触发串数据 | 未做状态锁与 revision 令牌 | `onPullDownRefresh`/`onReachBottom` 加 loading 锁；请求用 revision 令牌丢弃过期响应 | ★本补充 |

### 3.7 Git 协作

| # | 现象 | 原因 | 解决 | 来源 |
|---|---|---|---|---|
| 1 | commit 报 `Author identity unknown` | 未配置 Git 身份 | `git config --global user.name/email`（用注册 GitLab 的姓名邮箱） | Git指南 |
| 2 | pull 报「本地修改会被覆盖」 | 本地与远程改了同一批文件 | stash 三步法：`git stash save` → `git pull --rebase` → `git stash pop` | Git指南 |
| 3 | rebase 产生冲突（`<<<<<<<` 标记） | 双方改了同一段代码 | 手动合并 → 删标记 → `git add` → `git rebase --continue` → push | Git指南 |
| 4 | push 被拒绝（non-fast-forward） | 远程有新提交，本地落后 | **不要 `git push -f`**！`git pull --rebase` 整合后再 push | Git指南 |
| 5 | 本地配置被误提交，合作者启动失败 | `application-local.yaml`/`.env.local` 含环境信息 | `git update-index --skip-worktree <文件>`；验证 `git ls-files -v`（开头 S=生效） | Git指南 |
| 6 | pull 提示"本地已修改"但没改过 | skip-worktree 假象（远程更新了该文件） | 先 `--no-skip-worktree` 再合并 | Git指南 |
| 7 | `LF will be replaced by CRLF` | Windows 换行符警告 | **无害**，忽略 | Git指南 |
| 8 | 提交信息看不出改了啥，回溯困难 ★ | commit message 太笼统 | 按 `模块名：具体改动` 规范写，一个功能点一次提交 | Git指南 / ★经验 |

### 3.8 数据库与 SQL（★ 经验补充）

| # | 现象 | 原因 | 解决 |
|---|---|---|---|
| 1 | 查询慢/超时 | 缺索引或索引未命中 | 高频查询字段建索引（联合索引注意最左前缀）；用 EXPLAIN 验证 |
| 2 | 中文乱码 | 表/字段字符集不是 utf8mb4 | 建表统一 utf8mb4；连接串加 `characterEncoding=utf8` |
| 3 | 逻辑删除 + 唯一索引冲突 | deleted=1 的行仍占唯一键 | 唯一键设计考虑 deleted（如联合唯一含 deleted 或删除时改唯一字段） |
| 4 | 大文本字段（content 等）拖慢列表查询 | 列表也查了 text 字段 | 列表查询不 select 大字段；详情单独取 |
| 5 | `BETWEEN` 时间边界漏数据 | 时间精度到秒/毫秒，边界处理不当 | 明确闭/开区间；测试覆盖边界（如 `23:59:59`） |
| 6 | 状态字段用魔法值散落 SQL | WHERE 里写死 0/1 | 用常量/枚举 + `#{...}` 参数绑定 |

### 3.9 协作与流程（★ 经验补充）

| # | 现象 | 原因 | 解决 |
|---|---|---|---|
| 1 | 做到一半发现需求理解错了 | 未在开发前确认"待确认点" | 需求分析阶段强制闭环：歧义字段列清单找甲方确认，确认记录写进 day 文档 |
| 2 | 新表已上线但交付清单没标 DDL 状态 | 测试库已执行 ≠ 仅本地联调 | 交付清单固定含 DDL 状态列（测试库已执行 / 仅本地联调），上线前核对 |
| 3 | 联调时才发现接口字段对不上 | 前后端并行开发未对齐契约 | 契约先行：先定 VO 再并行开发；联调前先对一遍接口清单 |
| 4 | 改动跨模块（infra/system）影响面失控 | 未评估依赖模块 | 跨模块改动单独列清单审查（参考审查清单"共用基础设施改动"节），评估耦合度 |
| 5 | 分支长期不合并，冲突爆炸 | 大功能憋到最后才推 | 拆小步频繁提交推送；推送前必 `pull --rebase` |
| 6 | 上线后才发现权限没配 | 菜单 seed 只在本地产出 | 交付清单含菜单/权限/定时任务配置项，部署阶段核对生产 |
| 7 | 改了全局配置（字典/菜单/定时任务）不告知，他人配置被覆盖或联调信息差 | 缺乏信息同步机制 | 四类配置任何更新后**必须在群聊中告知**，含操作内容、影响范围、是否需前端配合 | ★本补充 |
| 8 | 新手开发者直接 SQL 创建角色/用户，权限遗漏或审计断裂 | 不了解管理端操作流程 | 必须通过管理端（系统设置 → 用户与角色）创建，**禁止直接 SQL 插入**；新手遇此类操作先找有权限的人协助 | ★本补充 |
